# 校园二手集市 —— 校园二手交易平台

面向校内用户的多角色二手闲置交易网站。B/S 架构，线上完成信息撮合、线下当面自提完成交易。

- **前端**：原生 HTML + CSS + JavaScript（ES Module，无框架、无打包器；fetch 调接口，切换页面不整页刷新）
- **后端**：Python Flask + Flask-SQLAlchemy + JWT(flask-jwt-extended) + bcrypt
- **数据库**：MySQL 8（InnoDB，utf8mb4），schema.sql 定义 14 张表 + 功能迭代新增 3 张（`messages`、`product_wants`、`post_images`），当前共 17 张表
- **地图**：腾讯地图 JS API（GCJ-02）；未配置 key 时自动降级为 canvas 自绘校园示意图

需求与设计依据见 [PRD-v2.0.md](PRD-v2.0.md)、[功能文档.md](功能文档.md)、[数据库字段归纳.md](数据库字段归纳.md)。
自测结果见 [docs/验收报告.md](docs/验收报告.md)。

## 一、快速开始

```bat
:: 1. 建虚拟环境并装依赖（已装好可跳过）
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt

:: 2. 建库建表（首次）
.venv\Scripts\python.exe manage.py init-db

:: 3. 写入示例数据
.venv\Scripts\python.exe manage.py reset-demo

:: 4. 启动
start.bat
```

浏览器打开 <http://127.0.0.1:5000>。

## 二、让网站一直挂着（推荐）

`start.bat` 是前台运行，**关掉命令行窗口服务就停了**。想让网站长期可访问，用下面这套：

| 操作 | 做什么 |
|------|--------|
| 双击 `start-service.bat` | 后台启动，**没有黑窗口**，日志写到 `logs\server.log` |
| 双击 `stop-service.bat` | 停止服务（按 5000 端口精确结束进程） |
| 看 `logs\server.log` | 访问日志与启动信息 |

**已配置登录自启**：启动文件夹里放了一个 `SecondHandShop.vbs`
（`%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\`），每次登录 Windows 会以无窗口
方式自动把服务拉起来。不想要就把它删掉，不影响手动启动。

它和 `start.bat` 的区别在 `service.py`：关掉调试模式与热重载（不会双进程、不会因为改文件自己
重启）、开启多线程，并且**自己把输出写进 `logs\server.log`**（所以能用 `pythonw.exe` 无窗口跑）。

> **局域网访问**：服务默认监听 `0.0.0.0`，同一 Wi-Fi 下的手机 / 别的电脑可以直接打开
> `http://<本机IP>:5000`。两步走：
> 1. **放行防火墙**：右键项目根目录的 `open-lan.bat` → 「以管理员身份运行」（只需一次；
>    它会放行 TCP 5000 入站并打印当前可用的局域网地址）；
> 2. **自检**：`.venv\Scripts\python.exe tools\lan_check.py` 会逐项检查监听地址、
>    局域网连通性、防火墙放行情况，并打印该用哪个地址访问。
>
> 只想让本机访问就设环境变量 `APP_HOST=127.0.0.1` 再重启服务（默认已开放到局域网）。
>
> ⚠️ **安全提醒**：开放到局域网后，演示账号（含管理员 `admin/123456`）在局域网内谁都能登录，
> 而管理员可以删商品、重置或恢复全部数据。长期开放前建议先把这些密码改掉。

## 九、在受限文件沙箱下开发时的两个坑（已解决）

如果本机 DSH 会话运行在 `workspace-write` 文件沙箱下，`pip` 会以两种方式失败：

1. **`tempfile.mkdtemp()` 创建的目录里无法再建文件**（`PermissionError [Errno 13]`），
   而 pip 全程用它建临时目录 → pip 必挂。
   → 用 `tools/sandbox_pip.py`：在导入 pip 前把 `mkdtemp` 换成 `os.makedirs` 实现。
2. **pip 的 HTTP 缓存目录在用户目录（工作区之外）不可写**，会让 pip **100% CPU 空转、零输出地假死**。
   → 所有 pip 命令加 `--no-cache-dir`。

完整可用的离线安装方式（本项目就是这么装起来的）：

```bat
set TMPDIR=%CD%\_build_tmp
.venv\Scripts\python.exe tools\sandbox_pip.py install --no-cache-dir ^
    --no-index --find-links wheels flask flask-sqlalchemy pymysql ^
    cryptography flask-bcrypt flask-jwt-extended
```

## 十、本机 HTTPS 被拦截时的 git 配置

本机装了 HTTPS 拦截工具（Steam++ / 瓦特工具箱，证书签发者为 `SteamTools Certificate`），
它会替 github.com 等站点签发自己的证书。表现是：

- 浏览器和 Python 走 **Windows 证书store**，所以访问正常；
- **git 用的是自带的 Mozilla CA 包**，不信任这张证书，报
  `SSL certificate problem: unable to get local issuer certificate`；
- 把 git 的 SSL 后端切成 `schannel` 又想用系统凭据时，会报 `SEC_E_NO_CREDENTIALS`。

本仓库采用的解法（**只影响本仓库**，不改系统证书store，也不关闭证书校验）：

```bat
:: 1. 从 Windows 证书store里取出拦截工具的根证书，追加到 git 自带 CA 包的副本上
.venv\Scripts\python.exe tools\build_git_ca.py

:: 2. 让本仓库的 git 使用这份 CA 包（文件放在 .git 下，不会被提交、不会被清理）
git config http.sslBackend openssl
git config http.sslCAInfo .git/git-ca-bundle.crt
```

> **更彻底的解法**：在那款工具里关掉「HTTPS 拦截 / 证书劫持」功能，之后就完全不需要这套配置。
> 毕竟它替换了所有网站的证书，本身也意味着你的 HTTPS 流量都经过它。

另外，推送时 git 需要调起系统凭据助手（Git Credential Manager），它是 msys 程序、要创建信号
管道；在受限文件沙箱下会报 `couldn't create signal pipe`，需要放宽一次权限才能完成推送。

## 十三、交易监管 / 卖家主页 / 好评率 / 私信（2026-10-15 这批需求）

### 1. 管理后台「交易管理」（需求①）

管理后台第 2 个页签，用于「看得到 + 能干预」：

- **实时列表**：进行中的交易（待完成）按「挂得最久」排前面，每行带买卖双方、商品名与**商品编号**、
  金额、自提点、状态、已进行时长；顶部 4 张总览卡（进行中 / 涉及商家 / 最长挂单 / 今日新增）。
- **自动刷新**：每 5 秒轮询一次（本项目不引 WebSocket）；切页签或离开页面会停掉定时器。
- **干预**：可「强制取消」（商品恢复在售）或「标记完成」，都先弹确认框。
  复用既有订单接口（`PATCH /api/orders/<id>/cancel|complete` 本来就对管理员开放），不另写一套状态流转。
- **动态监控时间线**：数据来自新表 `operation_logs`，记录「谁 · 何时 · 对哪个对象 · 做了什么」，
  覆盖发布/编辑/上下架/删除/彻底删除商品、下单/取消/完成交易/删订单记录、评价、举报，
  管理员的干预记为 `admin_order_cancel` / `admin_order_complete` 便于追责。
  日志与业务操作**同一事务**，不会「操作成功却没留痕」。

> **为什么必须加这张表**：只靠 `products.updated_at` 只能反推「这件商品最后一次被改的时间」，
> 看不出改了什么、更看不出是不是多人在同时改——需求里的「多商家同时编辑、多项交易并发」
> 必须靠留痕才看得到。

### 2. 卖家商品主页与「商家简介」（需求②）

- 入口：商品详情页的卖家昵称（信息区与下方两处都点得动）→ `#/seller/<uid>`。
- 顶部展示卖家**愿意公开**的信息：头像、昵称、商家简介、好评率与分级、在售件数、已售件数、
  加入时间、卖家编号（复用商品编号里的脱敏卖家码）。
- 商品流沿用主页同款卡片；默认「在售」，可切「已售」当作成交记录；支持关键词与分类筛选；
  **已下架与已删除的商品不展示**。
- 接口 `GET /api/sellers/<uid>` 刻意**不返回** `username`（登录名）与 `credit`；
  管理员没有卖家主页（404）。
- 「商家简介」= `users.bio`（≤100 字），卖家在「个人资料」页自己填、可留空，
  页面里还给了直接预览自己卖家主页的入口。

### 3. 商家好评率与分级（需求③）

| 项 | 口径 |
|---|---|
| 好评 | 4~5 星 |
| 好评率 | 好评数 ÷ 总评价数 |
| 统计范围 | **只统计「卖家作为被评方」的评价**——本项目评价是双向互评，`reviews` 里同时存在「买家评卖家」与「卖家评买家」，**必须关联订单判方向**（`reviews.reviewee_id == orders.seller_id`） |
| 分级 | ≥95% 优秀 / 85%~95% 良好 / 70%~85% 一般 / <70% 待改进 |
| 无评价 | 显示「暂无评价」，**不参与分级**（刻意用中性灰，不硬凑成「100% 优秀」误导买家） |

展示在商品详情页、卖家主页、个人资料页；**界面上取代信用分**，`users.credit` 保留在库里、
不删、不参与计算。好评率实时聚合、不加冗余列，避免「库里存的和评价对不上」。

> 踩过的坑：一开始按 `reviewee_id = 用户` 过滤，结果**卖家回评买家那条也算进了买家的好评率**。
> 双向互评里被评人有两个身份，光看 `reviewee_id` 分不出方向——必须 join 订单。

### 4. 私信页两个按钮（需求④）

「查看 TA 的商品」→ 卖家商品主页（**原来跳的是搜索页**，等于把买家从正在咨询的商品上甩走）；
「返回原商品」→ 买家原来浏览的那件商品详情页，**不是从商品页进来的会话就不显示**。
实现上把两个概念拆开：`productId`（这条消息针对哪件商品，发出去就清空）与
`originProductId`（买家从哪个商品页进来的，由 URL 的 `product` 参数带来）。
顺带把聊天头部的「信用分」换成好评率徽标（与需求③一致）。

### 5. 私信删除会话（需求⑤）

口径与项目既有删除语义一致——**只对我隐藏**：

- 我从会话列表移除它、我这边的历史从此刻重新计；
- **对方完全不受影响**，仍能看到全部聊天；
- 对方再发新消息，会话会重新出现在我的列表里（且只显示删除之后的新消息）。

实现：新表 `message_clears(user_id, peer_id, last_message_id)`，记「我清空到哪条消息为止」。
用**消息 id**而不是时间戳，避免「对方的新消息恰好与删除同一秒而被一起隐藏」。
会话列表、聊天记录、未读数三处都按这个下限过滤。

## 十五、商品编号 product_code

每件商品在发布时由**后端**生成一个可读编号，用作商品识别、卖家溯源、客服对账与后台定位。

```
[分类码4]-[卖家码4]-[日期码6]-[流水号5]          例：LF03-0002-260925-00006
  │         │         │        └── 该卖家发布的第 6 件（永不改变）
  │         │         └─────────── 发布日 YYMMDD
  │         └───────────────────── 卖家脱敏序号（users.seller_seq，非真实用户 id）
  └─────────────────────────────── 大类字母码（categories.code）+ 大类内小类序号
```

| 项 | 说明 |
|---|---|
| 生成时机 | 发布商品时、写库之前，**同一事务内**；前端不生成、不接收、不提交 |
| 不可变 | 一经生成永不改变：改分类/改名/改价/上下架/软删都不重算，分类码以**首次发布时**为准；编辑接口会丢弃前端传来的 `product_code` |
| 流水号 | 取「该卖家已有编号的**最大流水号 + 1**」——**不是 `COUNT(*)+1`**。因为本项目支持「彻底删除商品记录」（物理删），用计数会在删掉中间某件后与现存编号撞号，唯一索引拒绝 → 重试仍是同号 → 发布失败 |
| 卖家码 | 用户**首次发布商品时惰性分配**（`users.seller_seq`）。注意本项目「买家/卖家只是视角、不是权限」，任何普通用户都能发布，所以不存在「仅卖家有值」 |
| 无小类 | 小类段填 `00` |
| 未配字母码 | 回退用分类 id 补零 2 位，并打告警日志；到管理后台「基础数据」补配即可 |
| 展示位置 | 商品详情页、我的商品、我的订单、管理后台（**都是在既有信息区追加小号灰字，没有新增表格列**）；后台搜索框支持按编号搜索 |
| 订单留档 | 下单时把编号写进 `orders.product_snapshot`，商品被彻底删除后订单仍能显示原编号 |

**维护命令**

```bat
.venv\Scripts\python.exe manage.py migrate          :: 建字段（幂等，product_code 先允许 NULL 便于回填）
.venv\Scripts\python.exe manage.py backfill-codes   :: 存量商品补号 + 补大类字母码/小类序号/卖家码/老订单快照，最后收紧为 NOT NULL
```

> `schema.sql` 会与迁移保持同步（始终是全量现状），但 `init-db` 建完表**仍会自动补跑一遍迁移**——
> 这样将来新增迁移时不必记得手动补，也不会出现「建完表紧接着灌数据报未知列」。
>
> `seed.py` 建示例商品时会**即时生成编号**（`product_code` 是 NOT NULL，必须在 INSERT 前算好），
> 并且在建商品之前先备好大类字母码与小类序号，否则编号会退化成 `0100-…` 这种 id 补零形式。

## 二十三、头像显示错乱的修复（2026-10-17 需求①）

1. 反向验证时断言失败导致头像**没还原**（还清掉了一个残留在演示账号上的旧头像），把功能⑦「未设置头像时显示昵称首字」带红了

### 二十八·补记：折叠组「永远展开」的真因（2026-10-18）

上面那条修复（把展开状态挪进 `expandedGroups` 集合）解决的是"5 秒自动刷新把展开态冲掉"，
但用户复测后反馈**仍然不对：现在是"全都展开"**。复查发现真正的元凶是**样式**：

```css
.tl-group-items { display: flex; ... }   /* 作者样式 */
/* 浏览器默认：[hidden] { display: none } 优先级更低 → 被压掉 */
```

于是 **`hidden` 属性一直是 true、视觉上却永远可见**。实测（初始状态）：
`hidden=true, display=flex, height=356, visible=true` —— 点按钮只有文字在变，画面完全没动。

**修复**：`.tl-group-items[hidden] { display: none; }`（属性选择器 0,2,0 高于 0,1,0，不需要 `!important`）。

**测试为什么会"假绿"**：我原来断言的是 `panel.hidden`（属性），被 CSS 骗过；现在一律看**真实渲染**
（`getBoundingClientRect().height > 0` + 把 `getComputedStyle().display` 打进断言详情），并补了「初始必须收起」。
**反向验证**：临时撤掉那条 CSS → 功能56 立刻红 2 条，失败详情直接打出 `cssDisplay:"flex", height:356`。

**两条可复用的教训**：①**`hidden` 属性不是"绝对隐藏"**——只要作者给它写了 `display`，`[hidden]` 就失效，
必须自己补 `[hidden] { display: none }`；②**断言"元素是否可见"要看渲染结果（尺寸/计算样式），不能只看属性或类名**。

| # | 项 | 口径 |
|---|---|---|
| 1 | 交付层次 | **纯统计 + 可行性论证，不训练模型** |

### 一、四块新偏好（全部并进 `GET /api/admin/activities/profile`）

| 接口字段 | 内容 | 口径 / 权重 | 数据来源（不新增埋点） |
|---|---|---|---|
| `product_pref` | 商品偏好 Top5 + 小类占比 | 浏览×1 + **停留分钟×1** + 收藏×3 + 下单×4 | `user_activities` 商品页 + `favorites` + `orders` |
| `seller_pref` | 商家偏好 Top5 + 卖家集中度 CR3 + 回头率 | 同上，按卖家归并（商品页停留 + 商家主页停留都算） | ＋ `/seller/<uid>` 浏览、`follows` |
| `post_pref` | 帖子分区偏好（4 个 tag）+ 与全站占比的差值 | 按浏览次数计占比；`base_share` ＝ 全站同 tag 占比 | `/post/<id>` 浏览、`post_likes`、`post_comments` |
| `image_pref` | 图片偏好（个人 vs 大众）+ 头图/细节图拆分 | `view_weight()` 三层加权，见下 | `product_image_views` + `product_images` + `image_features` |

**图片偏好的三层加权**（`imaging.view_weight()`，可直接单测）：

```
权重 = max(停留秒, 1) × (第 2 张起 ? 1.5 : 1) × (该商品被收藏/下单 ? 2 : 1)
```

- 「≥1 秒」是**曝光下限**：只有"看过这张图"这一条记录、停留记为 0 时，也要算一次曝光，否则会被整体抹掉；
- 翻图是**主动行为**，比首图更能说明偏好，所以 1.5 倍；看完了真的收藏/下单是**结果信号**，2 倍；
- 个人与大众用**同一个公式**（大众按各人自己的收藏/下单状态算），差值才是"他比大众更偏好什么"，
  而不是"平台图库长什么样"——这是这一轮和上一轮「图像感知」最本质的区别；
- 画像弹窗里的两张卡：**「图片偏好（他 vs 大众）」**五行（冷暖/明度/饱和/疑似人像/画面繁简，右侧同时给
  `他% / 全站%` 与差值）与 **「头图 vs 细节图」**（两组各给张数、加权占比与一句话描述）。

**界面**：画像弹窗从 6 张卡扩到 **12 张**（新增商品偏好、小类偏好、商家偏好、帖子分区、图片偏好、
头图 vs 细节图），仍是手绘 SVG + `--chart-*` 主题色、不引任何图表库；`.ch-hlabel` 加了一条**单行截断**
样式（商品名/卖家昵称太长会换行，柱子就对不齐了），完整内容在悬停提示里。

### 三、图像识别与分析模型：要不要训练、需要什么条件、怎么训

#### 1. 现状数据量（2026-10-18 实测，这是判断的唯一依据）

| 项 | 数量 |
|---|---|
| 用户 / 商品 / 商品图 | 18 / 52（在售 39）/ 143 |
| `image_features` | 180 行 |
| **图片级埋点 `product_image_views`** | **101 条，只来自 3 个用户** |
| 帖子 / 收藏 / 订单 / 评价 | 6 / 5 / 13 / 6 |
| 有页面行为的用户 | 15（其中 4 个是真人，其余是测试账号） |

**结论先说**：以现在的数据量，**训练任何一个视觉模型都不成立**，硬做的结果是过拟合，
既无法在答辩/验收时证明"模型比不用模型更好"，也没有可比的基线。所以这一轮的交付是
**可复算的真实统计 + 相对基线**，并把"要训练需要什么"写清楚。

#### 2. 三条路线逐条判断

| 路线 | 需要什么 | 现在能不能做 | 判断 |
|---|---|---|---|
| **A 端到端视觉 CNN（自己训练）** | 几千~几万张**带标签**的图、GPU、调参周期 | 差 **2~3 个数量级**（143 张图、5 收藏 + 13 订单） | **不可行**。小样本必过拟合，验收无法证明有效 |
| **B 在现成特征上训练轻量排序/分类**（逻辑回归 / GBDT / LambdaMART） | 每个用户数百条"图 + 结果"样本；负样本 | 只有 101 条图片级记录、3 个用户，且**没有曝光与负反馈** | **暂不可行**，补齐埋点后可做（见下） |
| **C 预训练模型做嵌入**（ResNet / CLIP 离线 ONNX 推理，**不训练**） | 一份预训练权重（10~80MB）+ `onnxruntime`/`numpy` | 当前 `.venv` **连 numpy 都没装**（只有 Pillow），`wheels/` 里也没有 | **技术可行，但它是"不训练"**；收益只是能把图归成「白底棚拍 / 生活场景 / 人物试用 / 截图」，可解释性提升有限，成本是新增依赖 + 权重体积 |

**所以本轮的选择**：用 Pillow 做**真实可复算**的色彩统计（冷暖/明度/饱和/鲜艳度/边缘密度/肤色占比），
再加上「个人 vs 大众」的偏离与「头图 vs 细节图」拆分——这三样已经把"图片偏好"讲清楚了，
且每个数字都能拿笔算回来。

#### 3. 如果将来要训练，具体步骤（分五步，前置条件不满足就不要开始）

**第 0 步：补埋点（不可跳过）**

现在缺的不是模型，是**标签**：

- 图片级只有"看了第几张 + 停留毫秒"，**没有结局动作**：收藏/下单时他停在哪张图，后端并不记录 →
  需要记录 `favorites.current_image_index`（或独立事件表）；
- **没有曝光**：列表页卡片图、详情页缩略图被看到但不点击，现在完全没数据 → 分不清"不感兴趣"和"没被看到"
  （这是推荐系统的基本前提）；
- **没有负反馈**：滑过去、秒退、关弹窗都不记录 → 没有负样本，排序模型训不出来；
- **帖子图不参与**：`post_images` 只有 1 行，且不并入图片偏好。

**第 1 步：数据量门槛（给可验收的数字，低于门槛只做统计）**

| 目标 | 最低数据量 |
|---|---|
| 用户级图片偏好排序 | 图片级行为 **≥ 5,000 条**、覆盖 **≥ 200 用户**、**≥ 500 张**不同图片 |
| 图片语义分类（若做） | 每个类别 **≥ 100 张**人工标注 |
| 端到端 CNN（不建议） | **≥ 50,000 张**带标签图 + GPU |

**第 2 步：定义标签与口径（不新造标注，先从行为推导）**

- 正样本：同一次会话（≤30 分钟）内，对这张图停留 **≥ 3 秒**，且随后**收藏或下单**了该商品；
- 负样本：曝光但停留 **< 1 秒**、且没有下滑 → 判为"不感兴趣"；
- 抽样 200 条人工核对，**标签一致率 ≥ 85%** 才继续（不一致说明埋点口径有问题，先修埋点）。

**第 3 步：特征与基线（必须逐级对比，否则说不清模型有没有用）**

- 基线 0：纯热度（当前 `recommend` 的回落逻辑）；
- 基线 1：品类 + 价格带（现在就在用）；
- 特征 2：Pillow 的 5~8 维统计特征（本轮的产物）；
- 特征 3：预训练嵌入（128~512 维，路线 C）；
- 指标：**Precision@5 / NDCG@10 / 覆盖率**；划分**按用户切**（同一用户不能同时出现在训练与测试集），
  时间上取最后 20% 做测试集——否则会拿到虚高的离线指标。

**第 4 步：只训"轻量模型"（推荐到这一档为止）**

- 在 5~8 维统计特征（或 128~512 维嵌入）上训逻辑回归 / GBDT 排序；
- 参数几十~几万，**CPU 秒级**，不需要 GPU，也不影响现有接口的 3 秒预算（特征离线算好入库即可）；
- 评估：离线指标 + **影子上线**（同批用户 50/50 分桶，对比点击率 / 收藏率 / 下单率），
  线上无提升就回滚到统计口径。

**第 5 步：端到端 CNN（本场景不建议）**

只有数据量到 5 万张带标签、且有 GPU 时才考虑。校园二手只有 5 大类 21 小类、图片同质化严重，
端到端训练的收益远小于成本，不如把数据花在"曝光 + 负反馈"的采集上。

#### 4. 什么条件下才值得回来训练（触发条件）

1. 图片级行为 **≥ 5,000 条**且覆盖 **≥ 200 用户**（现在 101 条 / 3 人）；
2. 业务上需要区分**语义类别**（"简洁白底图 vs 生活场景图 vs 人物试用图"）——Pillow 的统计特征做不到这类判断；
3. 有 GPU，或允许离线推理权重（当前环境只有 Pillow，`wheels/` 里没有 numpy / onnxruntime）；
4. 有人愿意标注并复核 ≥ 100 张/类的图片。

#### 5. 现在这套统计的边界（诚实说明，界面也这么标）

- 冷暖/明度/饱和/鲜艳度/边缘密度是**真实像素统计**，任何一个数都能复算；
- **疑似人像 = 肤色像素占比**、**画面繁简 = 边缘密度**，都是**启发式近似**，不是人脸识别、不是目标检测；
- 停留用「相邻两条浏览记录的时间差」近似，超过 30 分钟按挂机截断，天然有误差；
- 大众基线样本很薄（只有 3 个用户有图片级埋点）→ 界面在样本 < 5 张时标「样本不足，仅作参考」；
- 想做"人物形象 / 物体形状"的**真正识别**，只能等第 3 节的条件成熟。

## 四十、「看过这个的人还看」——Amazon item-to-item 共视相似（2026-10-18）

**需求**：按 `docs/偏好分析设计.md` 的缺口清单与参考文献，把可借鉴的做法真正落成功能；第一批选
**Amazon item-to-item 协同过滤**（Linden/Smith/York, 2003）——它是文档里"数据够、能看见效果、不依赖新埋点"的那一项。

**算法口径（用户拍板：余弦归一，论文原口径）**：

```
同用户 30 分钟内先后浏览的两件商品 → 记一次共视（同一会话同一对只算一次）
view(x) = 看过 x 的会话数（同会话看多次只算一次）
sim(a, b) = co(a, b) / √(view(a) × view(b))
```

- 用**会话数**而不是浏览次数做分母，能同时压掉"热门商品霸榜"与"什么都看的人把所有商品拉得很像"两重偏置；
- 对比"纯共视次数"：后者会让最热的那件（高等数学）出现在每个商品的推荐里。

**实现**：

- 新增根目录 `similar.py`（**纯函数、可单测**）：`parse_page()`、`build_stats()`（返回 `co` 共视计数与 `pop` 会话数）、`similarity()`（余弦归一排序）；
- 新增接口 `GET /api/products/<id>/similar?limit=6`（`limit` 夹在 1~12）：**只在售、排除自己、过滤我拉黑的卖家**；
  返回 `list` + `basis`（每件标了推荐来源：共视/同小类/同大类/热门）+ `reason` + `co_view_pairs`；
  共视样本不足 6 件时依次回落**同小类 → 同大类 → 热门**，推荐位不留空；
- 前端详情页底部加一张卡「看过这个的人还看」：复用现有 `productCardHtml`/`bindProductCards`，
  **不动分栏与现有区块**；接口失败静默（推荐位不能影响商品本身能否打开）。

**实测（当前数据）**：商品页浏览 780 行、去重「用户-商品」对 476、30 分钟内共视对 **4514**；
商品 1 的推荐里 **4 件来自共视**（co 分别 3/5/2/2 次）、2 件来自同小类回落——稀疏度如实体现在 `basis` 里。

**测试**：
- 冒烟 11 项：算法直接单测（30 分钟截断、同会话去重、`2/√(4×3)=0.5774 > 1/√(4×1)=0.5`、路径解析）+ 接口
  （最多 6 件、不含自己、都在售、`basis` 合法、`limit` 生效、不存在返回错误）；
- 浏览器新分组 **67**（4 项）：区块出现、卡片 ≤6 且带封面、头部有推荐依据、点卡片能进详情。

**局限（写清楚免得误读）**：4514 个共视对分摊到 106 件商品仍然很稀，多数商品的推荐靠"同小类回落"补齐；
共视质量要等真实浏览积累。下一步按文档是「两阶段推荐 + 离线评估（Precision@5 / NDCG@10）」。
