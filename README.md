# 校园二手集市 —— 校园二手交易平台

面向校内用户的多角色二手闲置交易网站。B/S 架构，线上完成信息撮合、线下当面自提完成交易。

- **前端**：原生 HTML + CSS + JavaScript（ES Module，无框架、无打包器；fetch 调接口，切换页面不整页刷新）
- **后端**：Python Flask + Flask-SQLAlchemy + JWT(flask-jwt-extended) + bcrypt
- **数据库**：MySQL 8（InnoDB，utf8mb4），schema.sql 定义 14 张表 + 功能迭代新增 3 张（`messages`、`product_wants`、`post_images`），当前共 17 张表
- **地图**：腾讯地图 JS API（GCJ-02）；未配置 key 时自动降级为 canvas 自绘校园示意图

需求与设计依据见 [PRD-v2.0.md](PRD-v2.0.md)、[功能文档.md](功能文档.md)、[数据库字段归纳.md](数据库字段归纳.md)。
自测结果见 [docs/验收报告.md](docs/验收报告.md)。

## 一、快速开始

```bat
:: 1. 建虚拟环境并装依赖（已装好可跳过）
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt

:: 2. 建库建表（首次）
.venv\Scripts\python.exe manage.py init-db

:: 3. 写入示例数据
.venv\Scripts\python.exe manage.py reset-demo

:: 4. 启动
start.bat
```

浏览器打开 <http://127.0.0.1:5000>。

## 二、让网站一直挂着（推荐）

`start.bat` 是前台运行，**关掉命令行窗口服务就停了**。想让网站长期可访问，用下面这套：

| 操作 | 做什么 |
|------|--------|
| 双击 `start-service.bat` | 后台启动，**没有黑窗口**，日志写到 `logs\server.log` |
| 双击 `stop-service.bat` | 停止服务（按 5000 端口精确结束进程） |
| 看 `logs\server.log` | 访问日志与启动信息 |

**已配置登录自启**：启动文件夹里放了一个 `SecondHandShop.vbs`
（`%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\`），每次登录 Windows 会以无窗口
方式自动把服务拉起来。不想要就把它删掉，不影响手动启动。

它和 `start.bat` 的区别在 `service.py`：关掉调试模式与热重载（不会双进程、不会因为改文件自己
重启）、开启多线程，并且**自己把输出写进 `logs\server.log`**（所以能用 `pythonw.exe` 无窗口跑）。

> 服务只监听 `127.0.0.1:5000`，即同一台电脑的浏览器可访问、局域网其他设备访问不到。
> 需要局域网访问就把 `service.py` 里的 `APP_HOST` 环境变量改成 `0.0.0.0`。

## 九、在受限文件沙箱下开发时的两个坑（已解决）

如果本机 DSH 会话运行在 `workspace-write` 文件沙箱下，`pip` 会以两种方式失败：

1. **`tempfile.mkdtemp()` 创建的目录里无法再建文件**（`PermissionError [Errno 13]`），
   而 pip 全程用它建临时目录 → pip 必挂。
   → 用 `tools/sandbox_pip.py`：在导入 pip 前把 `mkdtemp` 换成 `os.makedirs` 实现。
2. **pip 的 HTTP 缓存目录在用户目录（工作区之外）不可写**，会让 pip **100% CPU 空转、零输出地假死**。
   → 所有 pip 命令加 `--no-cache-dir`。

完整可用的离线安装方式（本项目就是这么装起来的）：

```bat
set TMPDIR=%CD%\_build_tmp
.venv\Scripts\python.exe tools\sandbox_pip.py install --no-cache-dir ^
    --no-index --find-links wheels flask flask-sqlalchemy pymysql ^
    cryptography flask-bcrypt flask-jwt-extended
```

## 十、本机 HTTPS 被拦截时的 git 配置

本机装了 HTTPS 拦截工具（Steam++ / 瓦特工具箱，证书签发者为 `SteamTools Certificate`），
它会替 github.com 等站点签发自己的证书。表现是：

- 浏览器和 Python 走 **Windows 证书store**，所以访问正常；
- **git 用的是自带的 Mozilla CA 包**，不信任这张证书，报
  `SSL certificate problem: unable to get local issuer certificate`；
- 把 git 的 SSL 后端切成 `schannel` 又想用系统凭据时，会报 `SEC_E_NO_CREDENTIALS`。

本仓库采用的解法（**只影响本仓库**，不改系统证书store，也不关闭证书校验）：

```bat
:: 1. 从 Windows 证书store里取出拦截工具的根证书，追加到 git 自带 CA 包的副本上
.venv\Scripts\python.exe tools\build_git_ca.py

:: 2. 让本仓库的 git 使用这份 CA 包（文件放在 .git 下，不会被提交、不会被清理）
git config http.sslBackend openssl
git config http.sslCAInfo .git/git-ca-bundle.crt
```

> **更彻底的解法**：在那款工具里关掉「HTTPS 拦截 / 证书劫持」功能，之后就完全不需要这套配置。
> 毕竟它替换了所有网站的证书，本身也意味着你的 HTTPS 流量都经过它。

另外，推送时 git 需要调起系统凭据助手（Git Credential Manager），它是 msys 程序、要创建信号
管道；在受限文件沙箱下会报 `couldn't create signal pipe`，需要放宽一次权限才能完成推送。

|------|------|------|

## 十三、交易监管 / 卖家主页 / 好评率 / 私信（2026-10-15 这批需求）

### 1. 管理后台「交易管理」（需求①）

管理后台第 2 个页签，用于「看得到 + 能干预」：

- **实时列表**：进行中的交易（待完成）按「挂得最久」排前面，每行带买卖双方、商品名与**商品编号**、
  金额、自提点、状态、已进行时长；顶部 4 张总览卡（进行中 / 涉及商家 / 最长挂单 / 今日新增）。
- **自动刷新**：每 5 秒轮询一次（本项目不引 WebSocket）；切页签或离开页面会停掉定时器。
- **干预**：可「强制取消」（商品恢复在售）或「标记完成」，都先弹确认框。
  复用既有订单接口（`PATCH /api/orders/<id>/cancel|complete` 本来就对管理员开放），不另写一套状态流转。
- **动态监控时间线**：数据来自新表 `operation_logs`，记录「谁 · 何时 · 对哪个对象 · 做了什么」，
  覆盖发布/编辑/上下架/删除/彻底删除商品、下单/取消/完成交易/删订单记录、评价、举报，
  管理员的干预记为 `admin_order_cancel` / `admin_order_complete` 便于追责。
  日志与业务操作**同一事务**，不会「操作成功却没留痕」。

> **为什么必须加这张表**：只靠 `products.updated_at` 只能反推「这件商品最后一次被改的时间」，
> 看不出改了什么、更看不出是不是多人在同时改——需求里的「多商家同时编辑、多项交易并发」
> 必须靠留痕才看得到。

### 2. 卖家商品主页与「商家简介」（需求②）

- 入口：商品详情页的卖家昵称（信息区与下方两处都点得动）→ `#/seller/<uid>`。
- 顶部展示卖家**愿意公开**的信息：头像、昵称、商家简介、好评率与分级、在售件数、已售件数、
  加入时间、卖家编号（复用商品编号里的脱敏卖家码）。
- 商品流沿用主页同款卡片；默认「在售」，可切「已售」当作成交记录；支持关键词与分类筛选；
  **已下架与已删除的商品不展示**。
- 接口 `GET /api/sellers/<uid>` 刻意**不返回** `username`（登录名）与 `credit`；
  管理员没有卖家主页（404）。
- 「商家简介」= `users.bio`（≤100 字），卖家在「个人资料」页自己填、可留空，
  页面里还给了直接预览自己卖家主页的入口。

### 3. 商家好评率与分级（需求③）

| 项 | 口径 |
|---|---|
| 好评 | 4~5 星 |
| 好评率 | 好评数 ÷ 总评价数 |
| 统计范围 | **只统计「卖家作为被评方」的评价**——本项目评价是双向互评，`reviews` 里同时存在「买家评卖家」与「卖家评买家」，**必须关联订单判方向**（`reviews.reviewee_id == orders.seller_id`） |
| 分级 | ≥95% 优秀 / 85%~95% 良好 / 70%~85% 一般 / <70% 待改进 |
| 无评价 | 显示「暂无评价」，**不参与分级**（刻意用中性灰，不硬凑成「100% 优秀」误导买家） |

展示在商品详情页、卖家主页、个人资料页；**界面上取代信用分**，`users.credit` 保留在库里、
不删、不参与计算。好评率实时聚合、不加冗余列，避免「库里存的和评价对不上」。

> 踩过的坑：一开始按 `reviewee_id = 用户` 过滤，结果**卖家回评买家那条也算进了买家的好评率**。
> 双向互评里被评人有两个身份，光看 `reviewee_id` 分不出方向——必须 join 订单。

### 4. 私信页两个按钮（需求④）

「查看 TA 的商品」→ 卖家商品主页（**原来跳的是搜索页**，等于把买家从正在咨询的商品上甩走）；
「返回原商品」→ 买家原来浏览的那件商品详情页，**不是从商品页进来的会话就不显示**。
实现上把两个概念拆开：`productId`（这条消息针对哪件商品，发出去就清空）与
`originProductId`（买家从哪个商品页进来的，由 URL 的 `product` 参数带来）。
顺带把聊天头部的「信用分」换成好评率徽标（与需求③一致）。

### 5. 私信删除会话（需求⑤）

口径与项目既有删除语义一致——**只对我隐藏**：

- 我从会话列表移除它、我这边的历史从此刻重新计；
- **对方完全不受影响**，仍能看到全部聊天；
- 对方再发新消息，会话会重新出现在我的列表里（且只显示删除之后的新消息）。

实现：新表 `message_clears(user_id, peer_id, last_message_id)`，记「我清空到哪条消息为止」。
用**消息 id**而不是时间戳，避免「对方的新消息恰好与删除同一秒而被一起隐藏」。
会话列表、聊天记录、未读数三处都按这个下限过滤。

## 十五、商品编号 product_code

每件商品在发布时由**后端**生成一个可读编号，用作商品识别、卖家溯源、客服对账与后台定位。

```
[分类码4]-[卖家码4]-[日期码6]-[流水号5]          例：LF03-0002-260925-00006
  │         │         │        └── 该卖家发布的第 6 件（永不改变）
  │         │         └─────────── 发布日 YYMMDD
  │         └───────────────────── 卖家脱敏序号（users.seller_seq，非真实用户 id）
  └─────────────────────────────── 大类字母码（categories.code）+ 大类内小类序号
```

| 项 | 说明 |
|---|---|
| 生成时机 | 发布商品时、写库之前，**同一事务内**；前端不生成、不接收、不提交 |
| 不可变 | 一经生成永不改变：改分类/改名/改价/上下架/软删都不重算，分类码以**首次发布时**为准；编辑接口会丢弃前端传来的 `product_code` |
| 流水号 | 取「该卖家已有编号的**最大流水号 + 1**」——**不是 `COUNT(*)+1`**。因为本项目支持「彻底删除商品记录」（物理删），用计数会在删掉中间某件后与现存编号撞号，唯一索引拒绝 → 重试仍是同号 → 发布失败 |
| 卖家码 | 用户**首次发布商品时惰性分配**（`users.seller_seq`）。注意本项目「买家/卖家只是视角、不是权限」，任何普通用户都能发布，所以不存在「仅卖家有值」 |
| 无小类 | 小类段填 `00` |
| 未配字母码 | 回退用分类 id 补零 2 位，并打告警日志；到管理后台「基础数据」补配即可 |
| 展示位置 | 商品详情页、我的商品、我的订单、管理后台（**都是在既有信息区追加小号灰字，没有新增表格列**）；后台搜索框支持按编号搜索 |
| 订单留档 | 下单时把编号写进 `orders.product_snapshot`，商品被彻底删除后订单仍能显示原编号 |

**维护命令**

```bat
.venv\Scripts\python.exe manage.py migrate          :: 建字段（幂等，product_code 先允许 NULL 便于回填）
.venv\Scripts\python.exe manage.py backfill-codes   :: 存量商品补号 + 补大类字母码/小类序号/卖家码/老订单快照，最后收紧为 NOT NULL
```

> `schema.sql` 会与迁移保持同步（始终是全量现状），但 `init-db` 建完表**仍会自动补跑一遍迁移**——
> 这样将来新增迁移时不必记得手动补，也不会出现「建完表紧接着灌数据报未知列」。
>
> `seed.py` 建示例商品时会**即时生成编号**（`product_code` 是 NOT NULL，必须在 INSERT 前算好），
> 并且在建商品之前先备好大类字母码与小类序号，否则编号会退化成 `0100-…` 这种 id 补零形式。

### 1. 交易管理页签的「状态卡下钻」（需求①）

### 2. 动态监控：条目详情 + 多条件筛选（需求②③）

- **点任意一条**看详情：行为（动作名 + 动作码）、发起人（昵称/@用户名/身份）、
  **精确到秒的时间** + 「多久前」、相关交易的双方与金额与自提点与时间、
  相关商品的名称与编号与状态、评价星级内容或举报理由，以及可点的跳转按钮；
  对象已被彻底删除时如实说明。接口 `GET /api/admin/logs/<id>`。
- **筛选**：动作 / 发起人 / **商品（名称或商品编号）** / 订单号 / **动作时间区间**（含当天整天），
  可任意叠加、一键重置。商品与订单号这两种筛选要**跨表关联**：商品要命中「直接指向它的日志」
  以及「指向它相关订单/评价的日志」，光看日志表是查不出来的。

### 3. 举报审核：填写理由 + 私信反馈（需求④）

删帖、下架商品、驳回都改成**填写理由表单**（预设原因下拉 + 详细说明多行输入，≤200 字），
处理结果以平台私信反馈：

| 处理 | 原因候选 | 私信通知谁 |
|---|---|---|
| 删除帖子 | 违规内容 / 虚假信息 / 广告刷屏 / 人身攻击 / 涉及隐私 / 其他 | 帖子作者 |
| 下架商品 | 同上 | 商品卖家 |
| 驳回举报 | 证据不足 / 内容不违规 / 重复举报 / 已处理过 / 其他 | 举报者 |

原因清单由后端 `REPORT_REASONS` 统一提供（`GET /api/admin/reports` 带 `reason_options`）；
不传原因时默认「其他」，对老调用方保持兼容；处理动作会记进操作日志（可按 `report_handle` 筛）。

### 4. 详情页的「原路返回」（需求⑤）

管理后台进详情时带 `?from=admin`，详情页据此决定返回目标与按钮文案——
从举报审核进帖子/商品详情，返回回举报审核（不再是交流广场）；交流广场入口行为不变。

### 5. 卖家侧的交易收尾（需求⑥）

| 位置 | 进行中 | 已完成 / 已取消 |
|---|---|---|
| 买家「我的订单」 | 确认完成 / 取消订单 | 评价 / 删除记录 |
| 卖家「卖出订单」 | **确认完成** | **删除记录** |
| 卖家「我的商品」[已售] | **确认完成** | **删除订单记录** |

口径（用户拍板）：**买卖双方都能确认完成**——线下交付完成后任一方先点都合理，
