# 用户商品偏好分析：现状、缺口与落地路线

> 适用项目：校园二手集市（`D:\secondhandshop`）
> 版本：v1.0（2026-10-18）｜性质：**设计说明文档，不含代码改动**
> 读者：需要判断"还差什么、下一步写什么"的开发/验收者

## 〇、一页结论

1. **"分析用户商品偏好"这件事，主体已经跑通**：浏览行为、图片级停留、图片颜色特征、14 个画像维度、规则版"猜你喜欢"都已上线（见第 2 节）。
2. **当前最大的限制不是算法，是数据**：图片级埋点只有 **157 条、来自 5 个用户**，商品 106 件（在售 84）。任何需要学习的模型（协同过滤、排序学习、视觉模型）都还立不住，现有画像一律走**可复算的统计口径**并在界面标注"样本不足"。
3. **三个真实缺口**（第 3 节给出方案）：① 缺"曝光 / 负反馈 / 结局动作"三类埋点；② 商品**没有 tag 字段**（只有分类/小类/成色）；③ "形状/物体"只能近似，真正识别要视觉模型。
4. **建议的下一步顺序**：补埋点（P0）→ 商品标签体系（P1）→ 序列召回（P1）→ 图像模型（P2，先到数据门槛）。每一步都给了验收口径与"什么时候才值得做"的硬门槛。

## 一、需求与范围

用户原话（2026-10-18）：

> 如果我要分析用户的商品偏好，应该需要实现什么功能，是否有其他网购平台的相关算法作为参考，如何才能实现基于对用户浏览商品的数据（如浏览时长、所浏览的商品形状或颜色特征、商品的相应tag）进行用户画像绘制，对此提交一份说明文档。

据此确认的三个口径：

| 项 | 口径 |
|---|---|
| 文档定位 | **以现状为底稿**：盘点已实现 → 指缺口 → 给参考算法与分阶段路线（不是从零设计） |
| 商品 tag | **一期用现有维度（分类/小类/成色）跑通**，二期再建标签体系（第 3.2 节含库表草案） |
| 算法参考 | **平台做法 + 对应论文**，每条落到"本项目能用哪一部分" |

## 二、现状盘点（已实现 ✅）

### 2.1 数据层：三张表撑起画像

| 表 | 记录什么 | 关键字段 |
|---|---|---|
| `user_activities` | 登录/登出/页面浏览 | `kind(login/logout/page)`、`page`（如 `/product/12`、`/seller/4`）、`page_name`、`created_at` |
| `product_image_views` | 图片级：看了第几张、停多久 | `product_id`、`image_index`、`dwell_ms`、`created_at` |
| `image_features` | 每张图的像素统计（Pillow，上传时算好） | `warm`(暖色占比)、`light`(明度)、`sat`(饱和)、`colorfulness`、`edges`(边缘密度)、`skin`(肤色占比)、`dominant`(主色名)、`aspect`(宽高比) |

配套：`imaging.py` 提供 `analyze()`、`describe()`、`weighted_aggregate()`、`compare()`、`style_labels()`、`view_weight()`。

### 2.2 特征层：三个可复算的口径

- **浏览时长**：用"相邻两条页面记录的时间差"近似，>30 分钟按挂机截断；图片级直接用 `dwell_ms`。
- **图片偏好强度**：`view_weight() = max(停留秒, 1) × (第 2 张起 ? 1.5 : 1) × (该商品被收藏/下单 ? 2 : 1)`——即"注意力 × 主动翻图 × 成交回推"。
- **风格标签**：`style_labels()` 把一张图归成「偏暖/偏冷、明亮/中间调/暗调、画面简洁/繁复、疑似人像、色彩浓/适中/素净」，供"风格 × 行为结果"分组。

### 2.3 画像层：`GET /api/admin/activities/profile` 的 14 个维度

| 维度 | 字段 | 说明 |
|---|---|---|
| 用户类型 | `utype` | 大类 + 帖子 tag → 学业备考型/数码装备型…（最高占比 ≥40% 且浏览 ≥5 次才归类） |
| 价格带 / 活跃时段 / 深度广度 / 转化 / 停留 | `price_breakdown`/`hours`/`depth`/`conversion`/`dwell_kinds`+`top_dwell` | 规则统计 |
| 图片行为 | `images` | 头图党 / 细节党、平均停留 |
| 图像感知 | `image_perception` | 冷暖/明度/饱和/鲜艳度/边缘/肤色 汇总，人像与繁简**标注为近似** |
| 商品偏好 | `product_pref` | Top5 + 小类占比；权重＝浏览×1 + 停留分钟×1 + 收藏×3 + 下单×4 |
| 商家偏好 | `seller_pref` | Top5 + 卖家集中度 CR3 + 回头率（含商家主页停留） |
| 帖子分区 | `post_pref` | 四 tag 的浏览/停留/点赞/评论 + 全站 `base_share` 与 `diff` |
| 图片偏好 | `image_pref` | 三层加权后的个人值 vs **大众基线**（同权重聚合其他用户）、头图/细节图拆分 |
| 品类 × 图片特征 | `cat_image_pref` | 每大类的风格画像 + 全站同大类基线 |
| 风格 × 行为结果 | `image_outcome` | 每类风格标签的观看/成交/成交率，样本 <5 排最后并标"样本不足" |

展示：管理端画像弹窗 `openProfileCharts()` 共 14 张卡，手绘 SVG/HTML，不引图表库。

### 2.4 应用层

- **猜你喜欢** `GET /api/products/recommend`：品类命中×3 + 价位接近×1.5 + 热度 − 已看过×0.8，排除自己发布的；无画像按热度回落并返回 `personalized`/`reason`。
- **冷启动**：无画像/未登录一律按热度 + 最新，不做假个性化。

### 2.5 一次浏览到一条画像：端到端链路

以"小李看了《考研数学复习全书》的 3 张图、停留 12 秒、随后收藏"为例：

1. **采集**：切到 `/product/42` → 前端上报一条 `user_activities(kind=page)`；切换图片与离开页面时各上报一次 `product_image_views(image_index=0/1/2, dwell_ms)`。
2. **特征**：上传商品图时 `image_features` 已算好该商品的冷暖/明度/饱和/边缘/主色；画像时按 `image_index` 取对应那张图的特征。
3. **加权**：`view_weight()` 把 `dwell_ms`、`image_index≥1`、`该商品是否被收藏/下单` 折成一个权重。
4. **聚合**：按商品 → 小类 → 大类逐级汇总（`weighted_aggregate()`），得到"品类 × 图片特征""风格 × 行为结果"等中间结果。
5. **对照**：用同一套权重聚合**其他用户**的数据得到大众基线（`compare()`），差值才是"偏好"。
6. **呈现/应用**：画像接口把上述结果装进 `product_pref`/`image_pref`/`cat_image_pref`/`image_outcome` 等字段；`recommend_products()` 再用品类/价位/热度出推荐。

关键点：**每一环都可复算**——同一个 `dwell_ms` 序列，任何人重跑都能得到同样的数字；这也是当前阶段（数据少）比"训一个模型"更可信的原因。

### 2.6 数据现实（这是所有算法决策的前提）

| 项 | 数量 |
|---|---|
| 商品 / 在售 | 106 / 84 |
| 商品图 / 有图商品 | 314 / 106（平均 2.96 张） |
| `image_features` | 366 行 |
| **图片级埋点 `product_image_views`** | **157 条，来自 5 个用户** |
| 收藏 / 订单（成交） | 8 / 20（12 笔完成） |

结论：**够做统计口径，不够训任何视觉/排序模型**。这也是现有画像坚持"不训练、可复算"的原因。

## 三、缺口与方案（P0 / P1 / P2）

### 3.1 P0：补三类埋点（不改算法，先让数据能支撑算法）

现在缺的不是模型，是**标签**：

| 缺什么 | 为什么缺就不行 | 方案 |
|---|---|---|
| **曝光** | 列表页卡片图、详情页缩略图"被看到但没点"完全没有记录 → 分不清"不感兴趣"和"没被看到" | 前端 `IntersectionObserver` 上报 `event=exposure`；新增事件表（草案见下），保留 `product_image_views` 兼容 |
| **负反馈** | 滑过、秒退、关弹窗没有记录 → 排序模型没有负样本 | 复用同一张事件表：`exposure` 且 `dwell_ms < 1000` 视为弱负反馈 |
| **结局动作落到图** | 收藏/下单只知道"这件商品"，不知道"当时停在第几张图" → "成交回推"只能到商品级，不能到图 | `favorites` 增 `image_index`；`orders` 增 `image_index`（或写进 `product_snapshot`） |

事件表草案（迁移 `022_image_events.sql`，表数 26 → 27）：

```sql
CREATE TABLE IF NOT EXISTS image_events (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id    BIGINT UNSIGNED NOT NULL,
  product_id BIGINT UNSIGNED NOT NULL,
  image_index INT NOT NULL DEFAULT 0,
  event      ENUM('exposure','view','convert') NOT NULL,
  dwell_ms   INT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL,
  PRIMARY KEY (id),
  KEY idx_user_time (user_id, created_at),
  KEY idx_product (product_id, event),
  CONSTRAINT fk_image_events_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
  CONSTRAINT fk_image_events_product FOREIGN KEY (product_id) REFERENCES products(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

验收：曝光上报不影响页面性能（上报走批量/`sendBeacon`）、同一用户同一图 5 秒内曝光去重、`/api/activities` 概览能看到曝光量。

### 3.2 P1：商品标签体系（二期；一期先用分类/小类/成色）

**为什么要建**：给商品打"考研 / 全新 / 收纳 / 毕业出"这类自由标签，才能回答"他对哪类标签最感兴趣"，也让搜索结果与召回更有区分度。现有 `分类/小类/成色` 是有限枚举，表达不了"毕业清仓""宿舍神器"这类语义。

库表草案（迁移 `023_product_tags.sql`，表数 27 → 28）：

```sql
CREATE TABLE IF NOT EXISTS product_tags (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  product_id BIGINT UNSIGNED NOT NULL,
  tag        VARCHAR(16) NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_product_tag (product_id, tag),
  KEY idx_tag (tag),
  CONSTRAINT fk_product_tags_product FOREIGN KEY (product_id) REFERENCES products(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

配套改造清单：

| 层 | 改动 |
|---|---|
| 模型 | `models.py` 加 `ProductTag`；`Product.to_dict()` 带 `tags` |
| 接口 | 发布/编辑接 `tags`（≤5 个、每个 ≤8 字、去重，预设词 + 允许自定义）；`GET /api/products?tag=…` 支持筛选；画像加 `tag_pref`（权重同商品偏好口径） |
| 前端 | 发布页多选 chips（`pages/productForm.js`）、详情页展示（`pages/detail.js`）、列表筛选（`pages/search.js`）、画像卡一张「商品标签偏好」 |
| 数据 | `backfill.py` / `manage.py backfill-tags`：按商品名关键词自动打标（复用 `demo_images.PRODUCT_TERMS` 的思路，幂等） |
| 测试 | 冒烟：发带 tag 的商品、按 tag 筛、画像 `tag_pref` 结构；浏览器：发布页多选、详情页展示、筛选生效 |

**注意**：标签是"用户输入"，要做长度/个数校验与去重，展示前必须转义（走现有 `esc()`）。

### 3.3 P1：序列召回（把"看过什么"变成向量）

有了完整浏览序列，可用 **item2vec** 把商品学成向量（同一次会话里相邻浏览的商品视为近邻），用户向量 = 最近 N 次浏览的加权平均，再做近邻召回。相比现在的规则打分，它能捕捉"教材→考研资料→台灯"这种跨品类连带。

前置门槛：会话内序列 ≥ 5000 条（当前 `user_activities` 有 1.7 万条，但真实用户只有十来个 → **先等真实使用量**）；上线前必须与现有规则打分做离线对比（第 5.3 节）。

### 3.4 P2：图像"形状/物体"识别（先到门槛再谈）

现状只有近似：边缘密度（简洁/繁复）、宽高比、肤色占比。真正的"形状/物体"识别需要视觉模型，门槛与路线已写在 README 第三十八节：

- 图片级行为 **≥ 5,000 条**、覆盖 **≥ 200 用户**、**≥ 500 张**不同图片；
- 到门槛后先试"预训练嵌入 + 轻量排序"（CPU 可行），不下场训端到端 CNN；
- 评估看 Precision@5 / NDCG@10，且要**按用户切分**数据。

## 四、可参考的平台做法与文献

| 平台 / 论文 | 核心做法 | 本项目能用哪一部分 |
|---|---|---|
| **Amazon item-to-item 协同过滤**（Linden/Smith/York, IEEE Internet Computing 2003，[DOI](https://doi.org/10.1109/MIC.2003.1167344)） | 离线算商品两两相似度，线上查表出"看过这个的人还看" | 用 `user_activities` 的**共视矩阵**（同会话内商品对）做离线相似度，商品详情页加"相关商品"；数据少时它比矩阵分解更稳 |
| **阿里 DIN / DIEN**（KDD'18 [arXiv:1706.06978](https://arxiv.org/abs/1706.06978) / AAAI'19 [arXiv:1809.03672](https://arxiv.org/abs/1809.03672)） | 用 attention 对用户历史行为序列加权，捕捉"这次是被哪段兴趣驱动的" | 思路可借：把"停留时间长 + 主动翻图"当天然权重；**模型本身数据量不够，先别上** |
| **YouTube 两阶段推荐**（Covington et al., RecSys 2016，[dblp](https://dblp.org/rec/conf/recsys/CovingtonAS16.html)） | 召回（粗排几百件）→ 排序（精排几十件） | 本项目可先做架构分层：召回=品类/共视/热度，排序=现有规则→未来的 GBDT/LTR；把现有规则当 baseline 排序器 |
| **Netflix 推荐系统实践**（Gomez-Uribe & Hunt, ACM TMIS 2016，[dblp](https://dblp.org/rec/journals/tmis/Gomez-UribeH16.html)） | 排序 + 大规模 A/B 与离线指标的对应关系 | 借鉴它的**评估纪律**：离线指标（Precision@K/NDCG）+ 影子 AB 双轨，不拿离线提升直接当线上收益 |
| **item2vec**（Barkan & Koenigstein, [arXiv:1603.04259](https://arxiv.org/abs/1603.04259)） | 把商品序列当"句子"学词向量 | 第 3.3 节的序列召回，实现成本低（几十行训练代码） |
| **CLIP 多模态**（Radford et al., [arXiv:2103.00020](https://arxiv.org/abs/2103.00020)） | 图文对齐，可做"语义类别"零样本分类 | P2：解决"白底棚拍 vs 生活场景 vs 人物试用"这类 Pillow 统计做不出的判断 |

## 五、落地路线与验收口径

### 5.1 分三期

| 期 | 做什么 | 交付物 |
|---|---|---|
| **一期（现在）** | 用现有维度跑通：分类/小类/成色当标签，14 维画像 + 规则推荐 | 已完成（见第 2 节） |
| **二期** | P0 三类埋点 → 收敛画像口径；P1 商品标签体系（建表+接口+前端+回填+测试） | 迁移 022/023、`tag_pref` 画像卡、发布页与筛选 |
| **三期** | 序列召回（item2vec）→ 两阶段推荐架构；数据到门槛后再上图像模型/轻量排序 | 召回接口 + 离线评估报告 + 影子 AB 结论 |

### 5.2 每期都要过的验收

- **功能**：冒烟（接口断言）+ 浏览器分组（界面行为）+ E2E（页面不炸）；
- **口径**：所有偏好数字必须**可复算**（界面给公式说明）、必须带**大众基线**、样本不足要显式标注；
- **性能**：画像接口保持 3 秒内返回（现有冒烟有这条断言，新增查询不要引入 N+1）。

### 5.3 什么时候才值得上"会学习的模型"

| 目标 | 最低数据量 | 现在的量 |
|---|---|---|
| 用户级偏好排序（LTR/GBDT） | 图片/商品级行为 ≥ 5,000 条、≥ 200 用户 | 157 条 / 5 用户 |
| 协同过滤召回 | 有交集的用户-商品对 ≥ 数千 | 远不足 |
| 视觉模型（形状/物体） | 带标签图 ≥ 5,000 张（端到端需 5 万+） | 366 张特征、无标注 |

评估一律：**Precision@5 / NDCG@10 / 覆盖率**，数据**按用户切分**（同一用户不跨训练/测试），时间上取最后 20% 做测试集；上线前**影子 AB**（50/50 分桶）对比点击率/收藏率，无提升就回滚到统计口径。

### 5.4 合规与隐私边界

- 行为与画像数据**只对管理员可见**（`/api/admin/activities/*` 全部走 `admin_required`），普通用户看不到别人的画像；
- 画像里只出现"商品/品类/图片风格"这类对象信息，**不采集**设备指纹、精确位置等无关数据（`ip`/`user_agent` 仅作运维排查）；
- 若将来对普通用户展示"你的年度报告"这类页面，必须先明确哪些维度可对外，并给"关闭行为采集"的开关——**当前没有这个开关**，属于三期之后的选题。
